# Power-saving order intake batch

Canonical scope: `03-core-business.md#T-03.09.01.01`–`.03`, the order-wizard intake in `T-03.09.02.01`–`.08` and `T-03.09.03.01`–`.06`, plus the customer list/detail foundation in `T-03.09.04.03`–`.04`. This is a functional submission slice, not completion of the full power-saving epic.

Customers with an eligible Individual profile can select an available saving plan and one assigned hardware product, enter a bill identifier, choose or add an installation address, accept the current versioned agreement, review server-priced lines including gift discount and net VAT, and submit for staff review. The wizard saves its current inputs in session storage across reloads. Bill verification uses an optional deployment-configured provider with timeout, bounded retry and a circuit breaker; unconfigured or failed verification routes the order to staff review without discarding inputs.

Submission rechecks profile type, plan/hardware availability, address ownership, agreement version, gift eligibility, and the exact quote digest. One transaction creates the generic order, saving order and line/stage records, initial contract version, unpaid invoice, redemption and audit event. A same-user idempotency key returns the original result on retry; a database uniqueness rule rejects a second active order for the same bill identifier and plan. Invoice transitions synchronize the saving order's financial status. Customer order list and detail show the invoice/payment link, contract state, submitted values and five fulfillment stages.

The bill step detects an active duplicate before submission, linking an order on the same profile or directing the customer to support without disclosing another profile's order ID. The following criteria remain for later batches: an admin-controlled duplicate policy; document upload and comments on the order detail; post-payment amendment rules; staff approval, fulfillment actions, and cancellation review/refunds. The current duplicate policy always blocks an active match. The external bill provider requires `SAVING_BILL_VERIFICATION_URL` and `SAVING_BILL_VERIFICATION_TOKEN`; absence is a manual-review fallback.

Validation: migrated saving-order HTTP test covering Individual versus Legal access, quote/VAT, stale quote rejection, atomic order/contract/invoice creation, retry, duplicate protection, gift redemption and readback; pure amount-allocation tests; bilingual wizard/catalogue UI tests; API/web builds and API/web/DB types; i18n tests; changed-file lint; database snapshot, OpenAPI contract and backlog checks. The repository's existing bundle budget failure on `main` (auth entry and electricity bootstrap) also occurs on this batch. These measured entry sizes rose about 1.6–1.9 KB from the prior main CI run; new order pages are loaded separately.
