# Durable storage configuration

The storage settings page saves the active configuration in `app_config` under `storage.active`. Before the first save, API and worker operations use deployment S3 settings. After saving, every operation reads the durable configuration; a process restart or another replica uses the same version. Configuration reads use a separate short-lived direct database connection so a file operation inside a business transaction cannot exhaust its own pool.

Set `STORAGE_CONFIG_ENCRYPTION_KEY` to the same strong independent secret on every API and worker through the external runtime environment file. Secrets are encrypted using AES-256-GCM with authenticated context and random nonces. Back up the key separately from the database. The settings page never reads back the secret. Use the overlap procedure before changing the key. [Encryption key rotation](../security/security-verification.md#encryption-key-rotation).

A save tests both the server and browser endpoints, then rechecks current staff permission, version and object-location restrictions in a transaction. The configuration and audit record commit together. Failed connection tests, audit failures, revoked permissions and stale versions do not activate changes. Endpoint tests use ListObjects with a one-object limit and fixed failure messages. They do not establish bucket versioning, retention, legal hold or browser CORS correctness; validate those during deployment.

Private and browser endpoints independently fall back to the default endpoint. With all endpoints empty, the SDK uses the standard regional AWS endpoint. Endpoints must be HTTP(S) origins without embedded credentials, paths, queries or fragments. Browser PUT/GET signatures use the browser endpoint; server reads/writes and cleanup use the private endpoint.

The API and worker trust the exact origins in `S3_ENDPOINT`, `S3_PRIVATE_ENDPOINT` and `S3_PUBLIC_ENDPOINT` from protected runtime configuration. Set `S3_ALLOWED_ENDPOINT_ORIGINS` there to preapprove any additional custom origins, including virtual bucket hostnames when path-style addressing is disabled. The allowlist includes the scheme, hostname and port. Use HTTPS for public origins and reserve HTTP for explicitly approved private endpoints. Before deploying this check, verify that any existing durable origin is approved on every API and worker. The settings page can test and activate approved endpoints after the normal credential and object-location checks.

Storage records currently identify objects by key, without a per-record bucket/provider identity. Once any record exists, this UI refuses changes to bucket, region or endpoint locations. Credential rotation is allowed after testing. Moving files to another location needs a separate migration that preserves all financial, contractual and audit references. Never delete metadata to bypass this gate. The existing worker only cleans explicit committed deletion requests and retains signed records.

The activation test verifies listing permission and reachability; credential policies must also allow the specific required upload, read and cleanup operations. A database or decryption failure fails closed instead of silently using a different environment bucket. A successful local fixture is not evidence that production credentials, CORS, lifecycle rules or legal holds have been configured.

Each server-side S3 client opens its transport circuit after five unavailable responses or transport errors within 60 seconds. After 120 seconds it admits one recovery request with a deadline of at most 30 seconds. Set the `STORAGE_PROVIDER_CIRCUIT_*` values in the shared runtime environment to adjust the threshold, window and cooldown. SDK retries and multipart requests count when admitted to transport. The circuit returns a provider error when it blocks a request, so callers can preserve unconfirmed writes or cleanup work. Presigned URL generation uses the existing origin and object controls. The Storage and Uploads dashboard reports observed circuit states and transport failure share by API or worker target. [Storage and Uploads dashboard](../../deploy/monitoring/grafana-storage-uploads-dashboard.json).

Each SDK request has 30 seconds to receive response headers. Configuration probes use five seconds and a single attempt. S3 regional redirect retries are disabled. Metadata and error response bodies have a separate deadline of the same duration and a 10 MiB cap before SDK parsing. Successful object downloads have a 30-second idle timeout and a two-minute body deadline, with file-size and byte verification at the consuming operation.
