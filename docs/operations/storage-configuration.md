# Durable storage configuration

The storage settings page saves the active configuration in `app_config` under `storage.active`. Before the first save, API and worker operations use deployment S3 settings. After saving, every operation reads the durable configuration; a process restart or another replica uses the same version. Configuration reads use a separate short-lived direct database connection so a file operation inside a business transaction cannot exhaust its own pool.

Set `STORAGE_CONFIG_ENCRYPTION_KEY` to the same strong independent secret on every API and worker through the external runtime environment file. Secrets are encrypted using AES-256-GCM with authenticated context and random nonces. Back up the key separately from the database. The settings page never reads back the secret. Use the overlap procedure before changing the key. [Encryption key rotation](../security/security-verification.md#encryption-key-rotation).

A save tests both the server and browser endpoints, then rechecks current staff permission, version and object-location restrictions in a transaction. The configuration and audit record commit together. Failed connection tests, audit failures, revoked permissions and stale versions leave the active settings intact. Tests check listing access, upload a disposable object and compare its bytes after a signed download. Validate bucket versioning, retention, legal holds and browser CORS during deployment.

Use **Restore storage settings** to review a previous version and prepare a recovery draft. The history records only connection settings from revisions superseded after this feature is deployed. It excludes both credential fields. Activating a draft requires recent verification, a fresh full probe with current credentials and an unchanged active version. When explicit credentials are configured, restoring an earlier location requires entering the settings and the current secret through the normal storage form. The same location lock rejects moves while stored objects exist.

Private and browser endpoints independently fall back to the default endpoint. With all endpoints empty, the SDK uses the standard regional AWS endpoint. Endpoints must be HTTP(S) origins without embedded credentials, paths, queries or fragments. Browser PUT/GET signatures use the browser endpoint; server reads/writes and cleanup use the private endpoint.

The web CSP permits browser uploads to the application's own origin. Staging uses path-style signed URLs with `S3_PUBLIC_ENDPOINT` equal to `APP_PUBLIC_URL`. Before switching CSP to enforcement, verify the effective browser origin from `storage.active` or its deployment fallback. Exercise a bank receipt and a solar document upload through the public endpoint and verify the server readback of both files.

The pinned SeaweedFS 4.54 filer webhook authenticates with a bearer token. Its HTTP envelope carries the object key, event type and filer metadata. Keep notification delivery disabled until a sender supplies a verifiable signature, delivery timestamp and stable event identity. Continue to verify the reservation and stored bytes through the authenticated object API before making an upload available. [Pinned webhook sender](https://github.com/seaweedfs/seaweedfs/blob/5ef99c1d8dbbeb4a035c055e3b464620506aefac/weed/notification/webhook/http.go) · [Event payload](https://github.com/seaweedfs/seaweedfs/blob/5ef99c1d8dbbeb4a035c055e3b464620506aefac/weed/pb/filer.proto).

The patched sender opts in through `signed_bucket` and a protected `signing_key_file` containing a separate 32-byte key encoded as hex. Use a fixed HTTPS endpoint with a trusted certificate. The sender signs the exact event body, its stable ID and the delivery time. It emits one logical event per object version under the upload key namespace and filters directory updates and delete markers. Activate the notification target after verifying the receiving service and its durable replay handling.

The runtime storage client ignores ambient AWS SDK endpoint overrides, including `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3` and shared AWS profile endpoints. Configure custom origins through the Barghsa storage settings and protected `S3_*` variables. The standard AWS credential chain still applies when no explicit credential pair is configured.

The API and worker trust the exact origins in `S3_ENDPOINT`, `S3_PRIVATE_ENDPOINT` and `S3_PUBLIC_ENDPOINT` from protected runtime configuration. Set `S3_ALLOWED_ENDPOINT_ORIGINS` there to preapprove any additional custom origins, including virtual bucket hostnames when path-style addressing is disabled. The allowlist includes the scheme, hostname and port. Use HTTPS for public origins and reserve HTTP for explicitly approved private endpoints. Before deploying this check, verify that any existing durable origin is approved on every API and worker. The settings page can test and activate approved endpoints after the normal credential and object-location checks.

Storage records currently identify objects by key, without a per-record bucket/provider identity. Once any record exists, this UI refuses changes to bucket, region or endpoint locations. Credential rotation is allowed after testing. Moving files to another location needs a separate migration that preserves all financial, contractual and audit references. Never delete metadata to bypass this gate. The existing worker only cleans explicit committed deletion requests and retains signed records.

Credential policies must allow the required upload, read and cleanup operations. A database or decryption failure stops storage operations. Verify production credentials, CORS, lifecycle rules and legal holds directly on the selected bucket.

The configuration probe needs to read bucket versioning, write and read its generated `_storage_probes/` key, and remove the version it created. Grant `s3:GetBucketVersioning` and, for a versioned bucket, `s3:DeleteObjectVersion` scoped to the probe prefix. If the provider omits the write's version or the response is lost, the probe checks its own object metadata before deleting. The save fails if cleanup cannot be confirmed. Check the disposable prefix with the storage operator after an unconfirmed cleanup.

Each server-side S3 client opens its transport circuit after five unavailable responses or transport errors within 60 seconds. After 120 seconds it admits one recovery request with a deadline of at most 30 seconds. Set the `STORAGE_PROVIDER_CIRCUIT_*` values in the shared runtime environment to adjust the threshold, window and cooldown. SDK retries and multipart requests count when admitted to transport. The circuit returns a provider error when it blocks a request, so callers can preserve unconfirmed writes or cleanup work. Presigned URL generation uses the existing origin and object controls. The Storage and Uploads dashboard reports observed circuit states and transport failure share by API or worker target. [Storage and Uploads dashboard](../../deploy/monitoring/grafana-storage-uploads-dashboard.json).

Each SDK request has 30 seconds to receive response headers. Configuration probes use five seconds and a single attempt. S3 regional redirect retries are disabled. Metadata and error response bodies have a separate deadline of the same duration and a 10 MiB cap before SDK parsing. Successful object downloads have a 30-second idle timeout and a two-minute body deadline, with file-size and byte verification at the consuming operation.
