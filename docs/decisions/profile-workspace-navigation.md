# Profile workspaces and navigation

Customer profile controls share one directory bound to the current account and profile-context revision. The picker shows initials, a localized profile type, verification status and the selected choice. The compact header reads that same directory. It retains the separate customer/staff operating-context indicator. Profile management remains available from the picker.

The owner approved retaining the existing profile-context and fresh-navigation representations on 2026-11-06. The existing server resolves the active profile from the authenticated user's saved preference and current ownership or active-agent membership. Endpoints with explicit profile identifiers still authorize those identifiers independently. Selecting a profile changes that preference; it grants no role or commercial permission. Unverified profiles remain available for viewing, while existing server-side verification rules gate new commercial activity.

A switch captures its target and account context once. It requires both the exact successful response and a fresh directory confirming that target before replacing the workspace. The existing settings-command coordinator holds uncertain outcomes and only rechecks them with a read. It does not replay an unkeyed selection automatically. The full-page loading/recovery view blocks the previous workspace, including while its modal code loads. An explicit workspace reload restarts the view without sending another selection. Confirmed changes retain the existing private-query reset, old-request cancellation and cross-tab refresh.

Navigation still comes from current backend permissions and profile type. Local labels and icons never create grants or destinations. The router refreshes current authority rather than keeping an immutable permission snapshot for an entire browser session. Staff operation queues remain separate from a staff member's personal customer profile; the existing authorized context switch crosses that boundary.

Phone navigation retains primary tabs and the More sheet. The tablet sidebar uses a 60-pixel icon rail and expands through the menu button, keyboard focus or hover on devices that support hover. Full labels remain accessible to assistive technology. Desktop keeps the full sidebar. The compact header keeps branding, notifications and account/profile access; language and theme controls remain in its account menu.

Customer profile commands load only in customer workspaces. Rich choices and loading/recovery presentation load when used; the command owner remains mounted while those views load. Customer startup budgets explicitly include their workspace chunk and its static dependencies. The two profile interaction views share an additional 15 KB gzip gate. The existing More sheet has an explicit 35 KB interaction gate; its compact navigation bar remains part of startup accounting. Every original numeric route budget remains in place. A named dynamic-entry selector handles Rollup's hashed facade keys: missing or ambiguous names fail, and dependency traversal, deduplication, gzip accounting and Size Limit checks remain unchanged.

Responsive checks for these workspace journeys cover the required eight viewport widths. They do not certify every application page; the separate all-page viewport gate remains required before release acceptance.
