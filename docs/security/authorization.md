# Authorization policy

PostgreSQL supplies current account, session, ownership and role authority. The session guard checks expiry, revocation and operating context and loads current staff grants. The endpoint identifies the resource and action, applies its domain capability and checks the object's authorized scope before it returns private data or accepts a command. UI navigation only presents the actions available to the current context. [Session controls](session-lifetime.md).

The API's `AuthorizationService` resolves staff and profile capabilities. Staff decisions require an explicit staff operating context and an exact grant, explicit wildcard or current administrator authority. The agent guard and active-profile selector use the same capability matrix. The database still supplies current roles, verifies profile ownership and scopes resource reads and locks.

## Customer profiles

- Use the authenticated account's server-owned active profile preference or the endpoint's explicit profile ID. In either case, authorize that profile using its current owner or active agent membership. Switching profiles changes a preference. The same account must prove authority to use the new selection. [Owner decision on profile context](../decisions/profile-workspace-navigation.md).
- An agent's Manager, Finance and Legal roles contribute additive capabilities within one legal profile. Actual ownership comes from the profile's current owner. Domain operations apply their permission for the requested action and retain additional constraints such as commercial verification or a signature review.
- Endpoints using the agent permission guard must declare a capability on the handler or controller. The guard denies requests when that declaration is missing and gives handler declarations precedence.
- Read and mutate customer orders, invoices, contracts, wallet records, tickets and documents within the authorized profile or account. Use `activeProfileSql(permission)` for current selection and bind the returned profile ID together with the resource identifier in the business query. Apply both constraints before returning records or issuing a signed transfer. Keep exact amounts, terms and state transitions inside the domain's authoritative transaction. [Customer setup and delegation](../decisions/customer-setup-and-delegation.md).
- Consultation customer and staff reads bind invoice links to both the request and its profile. Invoice details apply the same scope to the consultation link. Customer information replies authorize the profile before locking the request. Staff financial reviews, completion, refunds and payment settlement use only invoices in the request scope. A mismatched current invoice blocks financial commands. Older mismatched references remain available for restricted reconciliation without contributing funds or exposing links in consultation responses.
- Solar list and detail reads scope the linked solar contract and use the initial invoice recorded for its current version. Solar document reads and per-file actions bind the upload, request and profile. Customer document submission verifies profile authority before locking the request. Staff contract creation and replay both require current invoice-write authority, and the source upload must belong to the same solar request.
- Shared contract lists and activation details expose the initial invoice only when it belongs to the contract and profile or to the same profile's order with no competing contract association. Financial review stops for reconciliation when that link disagrees. Contract document reads and signing receipts verify the file's profile, contract and exact version. Staff contract history reads retain current module permission and session checks for the full read.
- Saving list, detail and change commands use the saving profile to scope the commercial order, invoice and contract. Change review and confirmation apply that scope before locking financial records. Hardware history uses the same profile for linked adjustment invoices.
- Saving staff queues, reads and commands bind the saving order to the commercial order, contract, current version and original invoice. History binds revisions and amendments to their contract versions and checks the ownership of any linked address. Hardware upgrade previews and cancellation bind the charge to its original invoice before locking it. An invalid upgrade link stays out of customer invoice links and continues to block replacement hardware and delivery until it is reconciled.
- Saving invoice events allocate inventory and derive order payment status only from the original automatic invoice for the same order, contract and profile. Hardware charges verify their original invoice and contract version before applying or releasing a replacement. A charge with inconsistent ownership or amount stops for finance reconciliation. Cancellation and refund updates use the cancelled contract's profile when deriving financial closure. Existing records and the staff approval inventory path retain their original semantics.
- Contract cancellation verifies saving hardware credits against the original invoice, saving order, profile, contract version and recorded amount. An inconsistent link is excluded from the preview and blocks the decision for reconciliation. Saved decisions retain their original financial evidence and require valid invoice links before readback. Financial closure requires all refund obligations to match the recorded decision, invoice and profile. Cancellation request notices use service links only when the linked order or request belongs to the contract's profile.
- Invoice and receipt reads apply an overpayment credit only when its completed ledger row matches the receipt, profile and amount. Existing credits with matching ledger identity can still be read without optional allocation metadata. A conflicting credit or stored allocation returns a reconciliation error and cannot be replayed as a successful confirmation.
- Receipt previews and original downloads require an immutable storage record for the authorized invoice or wallet receipt. New copies record the exact receipt, profile and flow in the submission transaction. Historical copies remain readable through their receipt namespace or claim and compatible provenance. Finance queues resolve attachment evidence once per page. Unavailable or conflicting evidence yields no signed link.
- Wallet payment retries recheck the current invoice profile and the original completed debit. Online top-up callbacks use one lock per canonical order ID and check the retained signed payload on replay. A same-order unpaid event can still proceed to server verification when a paid delivery arrives. State updates keep the original gateway authority, and the gateway verification reference takes precedence when present.
- Wallet balance and history use the authorized profile throughout the read. Customer history also checks the active profile and can search its own receipt bank name and payer reference. Staff reconciliation history searches only visible ledger fields and never loads receipt metadata. Cursors remain compatible and never replace the current authority checks.
- Signed chargebacks verify the original online credit and require a completed reversal for the same wallet, original transaction and opposite amount. Conflicting evidence produces a Finance alert without a second reversal or changes to historical records. The dashboard holds current Finance authority through the read and omits inconsistent ledger links.
- Reconciliation list and detail reads hold the current staff session and view grant. Lifecycle commands use the resolve grant and return the exact exception state produced by their audited transaction. Stored scanner details remain diagnostic evidence, and linked wallets and invoices enforce their own read grants.
- Failed-job reads hold current staff authority through the response data read. Retry and resolution retain live permission and step-up. Job receipts expose the worker's triage counters and status flag, with the stored payload available for restricted operational investigation.
- Invoice correction retries verify the source and result profiles, linked business records and review evidence before returning invoice lines. New adjustment approvals bind the invoice profile, and legacy approvals recheck it against the profile locked for resolution. Electricity replacement also verifies the order, contract and current activation requirement before changing its invoice link.
- Manual invoice review and issuance require any linked contract to belong to the selected profile. Retries hold the original invoice and verify its profile, type, contract, and issue audit before returning lines. Due-date overrides respect the invoice's payment opening, and the staff receipt only shows an override that matches the current deadline.
- Refund decisions and readback bind the refund, invoice, profile and destination. An approval or settlement receipt must match that scope and amount before it can authorize a payment or appear as evidence. A matching legacy electricity refund without a terminal decision still requires current Finance authority and the applicable approval. The wallet worker reuses the invoice receipt credit checks when deriving legacy allocations. A conflicting allocation leaves the obligation visible and retryable for reconciliation, with no new wallet credit.
- Electricity increase and price adjustment endpoints bind the contract, order, profile and invoice lineage before showing terms or quoting a financial basis. Invalid linked invoices stay out of public receipts. The public increase signature receipt identifies the request and includes the signer, time, amendment digest and amount. Stored session and network evidence remains in the restricted signed record.
- Electricity increase settlement and expiry validate the same relationships before changing a request or its charge invoice. An invalid link leaves the records intact for reconciliation. The worker reports `electricity_increase_scope_requires_reconciliation` in the failed-jobs ledger and continues processing valid requests. An authorized finance operator can locate affected records using a read-only query for pending, awaiting-signature or awaiting-payment requests where `electricity_increase_has_scope(r)` is false. Verify the originating contract, order and signed evidence before any approved correction.

Both notification inbox APIs recheck profile selection and notice ownership in
their resource queries. The account and session stay locked until the response
is authorized or the read-state change commits.

## Staff capabilities

- Staff sessions use the union of current database role capabilities for Customer Support, CRM and Verification, Finance, Legal and Contracts, Operations and Admin. A matching permission, explicit wildcard grant or current administrator authority is required. Staff account status permits staff context. Each protected operation still checks the required capability.
- Apply resource and assignment scope when the domain requires it. Explicit module-wide document read grants retain their approved scope. Distinguish read, write, approval and override capabilities, and require fresh step-up for designated high-risk actions. [Verification authority](../decisions/verification-policy.md).
- Recheck current session, capability and scope inside the protected decision when concurrent role removal, ownership changes or expiry could invalidate it. Preserve required CSRF proof, audit and idempotency across retries. Keep protected audit records separate from general diagnostics.

Staff role replacement requires the dedicated role capability and recent OTP
proof on the live session. Financial confirmations, refunds, contract decisions
and provider credential changes check their operation-specific capability and
step-up proof. A review can return the authorized consequences before step-up.
The command that changes state checks the proof before applying those effects.
Verification provider configuration writes and circuit-breaker resets also
require fresh step-up. The verification adapter remains a development stub.

Ownership transfers, role changes and protected identity edits write their
audit rows within the business transaction. The rows identify the actor, the
affected record and the previous and resulting authority or identity values.
An audit failure rolls back the change.

## Background and external work

- A worker acts on an authorized durable record with an operation-specific claim or lease. Before publishing a private result, recheck its current ownership or grant and enforce its result scope. Preserve transaction and provider idempotency boundaries when a retry is allowed. [Async jobs](../operations/async-jobs.md).
- The assistant reads published knowledge within the current audience and slot. Its launch scope permits read-only guidance. Session, operating context, publication and output checks determine what an answer can include. [AI inference](../operations/ai-inference.md).
- Signed provider callbacks prove the expected issuer, message and replay boundary independently of customer or staff sessions. Resolve the referenced durable intent before accepting a status or financial change. [Staging payment verification](../operations/staging-payment-sandbox.md).

The model-test worker rechecks the requesting staff grant before calling the
provider. The profile-export worker checks the current owner, active profile
and job lease before collecting data and before publishing the result. Export
downloads and document links check the current session and scope before signing.
The customer and staff application paths share the same profile and capability
rules at those boundaries.
